# 用法七：用声明服务管理生命周期钩子与协议

生命周期钩子和协议约定都可以组织为可查询的声明：描述什么时候使用、指向哪里、输入输出是什么，以及与其他条目的关系。LayerWeave 提供存储、层级、关联和修改记录，消费这些声明的工具负责解释与执行。[返回开发指导](README.md)。

本篇是一种数据组织方式，不新增内置钩子执行器、事件总线或协议解析服务。

## 将声明作为条目组织

```text
声明目录（project 或一个 root）
├─ 生命周期（层）
│  ├─ 内容更新后（事件对象）
│  ├─ 重建索引（处理器对象）
│  └─ 刷新摘要（处理器对象）
└─ 协议约定（层）
   ├─ 检索结果 v1（协议对象）
   └─ 检索结果 v2（协议对象）
```

这里的“事件对象”“处理器对象”“协议对象”是业务角色，不是已提供的 Python 类型。可以先使用现有层/对象保存 information；需要专用封装时仍遵守一份 Python 类对应一份 TOML 的方式。无需时间含义的条目可以采用[序号位置](02-ordered-metadata.md#用序号组织条目)。

| 声明 | 对象可以记录的内容 | 常见查询 |
|---|---|---|
| 生命周期事件 | 名称、触发时机、携带的数据约定 | 内容更新后有哪些处理器 |
| 钩子处理器 | 用途、实现入口、适用事件、顺序约定 | 某处理器被哪些事件使用 |
| 协议或接口约定 | 明确版本、输入输出定义、示例或原文位置 | 某组件采用哪个版本、谁还依赖它 |

这些内容由工具按需选择，不构成新的内核必填字段。

## 生命周期关系与级联

可以用 bind 保存如下关系：

```text
触发关系：内容更新后 → 重建索引 → 刷新摘要
协议采用：重建索引 → 检索结果 v1
```

同一数据库内的层/对象可以跨 project 关联。关系用于查找挂载位置、追踪依赖和展示调用链；实际执行器需要约定不同关系的含义、执行顺序及循环如何结束。不能将一个对象的所有 bind 都无区别地当成执行边。需要单独的关系类型、条件等字段时，可由工具使用自己的关系表，见[工具表接入](03-managed-tables.md)。

前提：connection 已打开，declarations_project_id 和 event_object_id 指向上例中真实存在的事件对象。

```python
from layerweave.support.api import read_bindings

bindings = read_bindings(
    connection, "object", declarations_project_id, event_object_id,
    direction="outgoing",
)
```

这返回直接关联，不触发钩子，也不自动装载目标。需要沿关联多步查看时使用现有 walk_relations；参数见[关联展开](../../src/layerweave/tool/builtin/usage/GUIDE.md#沿关联展开)。查询关系与执行动作分别由相应工具处理。

## 协议管理统一的是查找入口

协议原文可以保存在对象 information 中，也可以只记录版本、用途和正式定义的位置。例如已有 JSON Schema 或代码中的接口声明，就让目录指向它，展开时由读取工具取得原文；有必要时也可以把对象本身作为执行端读取的正式定义。

同一协议保持清楚的定义来源，避免文件和对象中的两份副本各自手工更新。对被引用的不同协议版本，可使用不同对象保存，bind 指向明确版本；LayerWeave 的改动日志用于追踪编辑历史，不自动替工具定义协议版本。

组件采用协议、协议之间声明的兼容或替代关系，也能保存和查询。真正的格式校验、版本适配或协议通信，需要消费端实现；建立关联本身不证明它们兼容。

## 保存与查询沿用原有能力

声明仍是普通记录，通过 write 原语或现有工具修改，复用事务、日志和历史能力。需要一次保存声明与关系时，见[事务内组合](04-composing-tools.md)；需要按后续变更更新目录缓存时，见[持续读取变化](05-incremental-reading.md)。

这类声明服务可以独立于 AI 使用。要把目录提供给 AI，可叠加[统一 MCP 入口](06-mcp-components.md)；要划分多个声明目录及其消费范围，可结合 [project 分区技巧](tip-project-scopes.md)。目录的定义不要求所有消费者采用相同的执行框架。
