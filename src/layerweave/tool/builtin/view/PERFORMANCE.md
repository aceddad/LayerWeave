# 视图性能测量与开发

用 view_bench 检查视图改动，用浏览器交互验收检查功能是否保留。性能数字依赖场景和机器，不能代替吸附、拼接、截图、插件等行为测试。视图的使用方法见[README](README.md)，量具实现见[bench.py](bench.py)。

## 先跑合成项目

在已安装视图包的 Python 环境执行：

~~~powershell
python -m layerweave.tool.builtin.view.bench --objects 800 --rounds 3 --json
~~~

不给数据库时，工具创建临时合成库和生成的图片、音频，结束后清理。合成项目固定为 240 秒，包含文字、图片、批注、音频；批注层按现行规则不显示在画布。对象增加时，每个对象的时间跨度变短，所以 800、5000、10000 的缩略图数量不会按比例增长。

也可以指定需要检查的项目：

~~~powershell
python -m layerweave.tool.builtin.view.bench DATABASE --project 1 --rounds 3
~~~

数据库只读。测试使用独立本机状态目录、临时插件清单和浏览器配置，页面以正常模式加 record=0 打开，不写批注、折叠或用户排版。浏览器禁用扩展、同步和后台联网；窗口为 1536×760，设备像素比例为 1.25。

## 五项门槛

返回的 rows 保留原来的五个 key，数值门槛不变：

| key | 实际测量 | 门槛 |
|---|---|---|
| open | 导航开始到首个对象进入 DOM | ≤ 2 秒 |
| click | 点选事件计时的中位数，默认最多取 10 个有效样本 | ≤ 120 毫秒 |
| board_drag | 拖动画板期间的 rAF 间隔 p95 | ≤ 33 毫秒 |
| zoom_pan | 放大后局部平移的 rAF 间隔 p95 | ≤ 33 毫秒 |

0.23.0 以前还有 zoom_pan_plugin（同样的平移，加上实际绘制文字格子的基准插件）。插件画格子在 0.23.0 收回，这一项随功能一起去掉，不是为了通过门槛。

open 仍用原有字段名，但显示名称明确为“首个对象进入 DOM”。这不代表媒体已画完、整页可操作，也不包含启动浏览器进程的时间。后续交互另等正常模式的媒体绘制工作完成。

点选前会定位实际对象；只有点选后目标确实选中，才保留样本。浏览器事件计时不报告小于 16 ms 的事件，这些样本按 16 ms 记录。它是事件响应的观察值，不是所有异步内容加载完毕的时间。

## 看有效性，再看数字

rows.status 的含义：

| status | 含义 |
|---|---|
| passed | 本项各轮都有有效样本，中位数不超过门槛 |
| exceeded | 测量有效，但中位数超过门槛 |
| invalid | 至少一轮未有效测量，不能据此判定通过 |

invalid 是量具没有取得可比较的样本，例如视口为空、目标被完全遮挡、图片没画出、输入被拒绝、拖画板时触发了边缘自动平移。它不是项目写入失败，也不是断言视图一定存在性能回退。原因在 rows.issues 和每轮 runs 下的 diagnostics 中。

部分轮次无效时，value 仍可展示有效轮次的中位数，ok 为 false；不能用其余几轮的好成绩掩盖无效轮次。CLI 全部通过返回 0，超过门槛或测量无效返回 1，无法启动或执行测量返回 2。

## 输入、帧与松手收尾

每次拖动默认发送 120 次有限的鼠标移动，按主机时钟安排在 2 秒内。发送下一次移动不等待页面对上一次的应答。浏览器可能合并输入，所以同时记录：

- sent_moves_ms：实际发送时间。
- pointers、actual_pointer_events：页面收到的事件及数量。
- input_displacement、actual_displacement：要求与实际移动距离。
- activation_displacement：画板拖动跨过启动阈值的小位移。
- cdp_errors：浏览器拒绝输入的错误。

画板拖动先用小位移激活，再完成剩余路径；总输入位移不变。平移使用 React Flow 原有的鼠标中键拖动，新旧构建使用同一种输入方式；这可以在带 nopan 标记的节点上正常平移，不伪造 transform 或改动产品交互设置。画板标题先通过这一正常手势移入视口内部，产品的自动平移仍启用；测量发现视口跟着变动，会将该轮标为无效。

diagnostics 中的 active 单独保存活跃拖动的 p95_ms、max_ms、sample_count、over_33_ms；松手后的等待不会稀释活跃帧分布。帧样本很少时，p95 可能等于最大值，应当按量级理解，不作稳定尾部百分位承诺。

first_callback_ms 和 release_callback_ms 分别表示按下、松手后第一次动画帧回调的等待。它们使用同一 performance.now 时钟，和用 rAF 时间戳相减得到的帧间隔分开。回调执行不等于像素已经呈现在屏幕上，rAF 也不证明每一帧都呈现了新内容。判断偶发卡顿时必须同时查看 max_ms，不能只看中位 p95。

拖动前会进行短暂往返平移作为热身。它用于比较连续操作，不能把热身改善全部归因于显卡频率：解码、缓存、脚本编译和系统负载也可能参与。click 的 first_ms 保留该点选序列的第一个样本；由于此前已经定位和缩放，它不是浏览器刚打开时的冷交互时延。需要研究冷交互时应另开明确的场景。

## 大项目与绘制就绪

量具通过对象编号定位具体对象，再围绕它实际可命中的位置缩放。缩放至少到 1.6 倍，必要时继续到格子可点选的大小；不会把整条长轨道的中点当成必然有内容的位置。

最小宽度的对象可能互相遮挡。命中检查会尝试对象与视口交集内的多个位置，并用 elementFromPoint 确认点击归属；完全被覆盖就报告无效，不会改动内容或点邻居冒充成功。局部平移的开始和结束也检查内容，空画面的快速帧不能通过。

大项目中，缩放会同时加宽贴住左侧的层名列，可能遮住原本定位在画面三分之一处的对象。量具遇到这种情况，会通过真实中键平移把目标移到层名列右侧，再继续围绕同一对象缩放；新旧构建使用同一规则，保留层名和全部对象。仍无法取得实际命中时才标无效。

新视图提供两个只读观察接口：

~~~javascript
await window.__layerweavePaintIdle();
window.__layerweavePaintState();
~~~

它们等待正常模式中已经启动的媒体工作，不切换 capture、不改变加载范围。图片就绪按可见对象的 data-media-state 判断；共享轨道画布不再要求每个对象都有一个 canvas。

旧版网页没有这些观察接口时，量具使用较弱的可见 DOM/媒体稳定检查，并在 ready.method 标成 legacy_visible_dom；新版本为 paint_queue。旧检查不能证明媒体都已画完，因此报告中应保留就绪方式。

capture 模式用于截图，会改变视角、细节或加载策略，不能用它的 ready 标志代替正常浏览性能测量。

## 共享媒体的范围

主画板中的图片、可抽帧的视频封面、普通音频波形由 TrackMedia 管理，按轨道分块贴图；对象 DOM 继续负责点击、文字、标记和关系连接点。侧栏、一览列表和 media=legacy 对照路径仍使用独立媒体元素。不能按“一个对象一个 canvas”估计当前主画板的绘制成本。

图片和服务端视频帧直接从解码源裁剪到目标 tile，不先画成两级中间位图。视频宽度达到首尾帧显示条件时，两端分别按 64 CSS 像素的实际目标准备；中间纯色区域由对象的 CSS 背景绘制，不因视频很长而分配一整条高清位图，也不让整条对象的 2048 限制压低端帧清晰度。

图片源按内容区域大小、镜头缩放、DPR 及 cover 裁剪比例选取 160/320/640/1280/2048 档，不仅按高度选择 160/320。后端向上选择最近一档并封顶 2048，原图更小时不放大；无 FFmpeg、SVG/GIF 或缩图失败仍回退原图。高清准备完成前保留已有画面，内容或来源变化仍按 source 版本重新获取。提高源图档位会增加加载和解码缓存成本，不代表画布像素密度也提高。

共享画布密度仍是镜头缩放乘 DPR，没有全局双倍密度。图片缓存区分正在使用的资源和无人引用的旧资源，闲置资源按最近使用顺序保留至多16项、且解码像素估算不超过64 MiB；旧档位可被回收。这限制的是闲置缓存，不是承诺整个页面固定内存上限。对象移走后已空的tile也会释放。

普通音频波形沿用原来的能量采样和绘制算法，立即开始加载，缩小到其他媒体只画色块的档位时也照常显示。其源位图按对象内容的 CSS 尺寸与 DPR 采样，不乘镜头缩放；内层宽度上限为 4096、内层高度上限为 512。

共享 tile 的宽、高都不超过 2048 设备像素。超长图片跨越过多 tile 时，用单个原生图片元素显示所选源，保留裁剪与圆角，避免不断分配 tile 或先压成很矮的整对象位图。音频仍保留按原尺寸规则生成的独立画布回退；超长音频内层上限为 4096×512，外层另含背景与边框，可能略大于内层，也不受共享 tile 的 2048 上限约束。视频端帧只按两端局部范围占用 tile。

准备、普通波形绘制和最终贴图共用同步预算队列；异步准备的结果只在当前代完成后贴图。屏幕外对象的 DOM 仍保留，媒体的原有加载范围和显示规则不因共享而取消。

## 与旧构建比较

~~~powershell
python -m layerweave.tool.builtin.view.bench --objects 800 --rounds 3 --baseline D:/bench/before-web --json
~~~

baseline 指向含 index.html 的构建目录，不是前端源码目录。两份网页使用相同的服务实现、合成数据和量具，测试顺序交替并反转先后：三轮为 A/B/B/A/A/B。结果包含 order、浏览器版本、当前与基线构建的 SHA-256。

保留所有轮次，先确认实际对象、画布、缩放、媒体与选择状态可比较，再观察配对变化。源码改变后保存新的结果，不能把另一次构建、旧版输入脚本或不同合成器的数字混成同一条曲线。这里的比较只覆盖网页构建；若服务端也改了，需另做端到端对照。

本机高负载、供电状态、浏览器和显卡驱动都会影响结果。有效的改善可以来自更少的重复工作；不能只凭隐藏 canvas 后变快，就认定是 GPU 执行时间或图层数的单一原因。

## 修改源码与验收

前端源码在仓库 frontend/view；构建结果随视图包分发。常见修改位置：

| 工作 | 入口 |
|---|---|
| 输入、有效性、统计与基线顺序 | 本目录 bench.py |
| 瞬时拖动、吸附与拼接 | frontend/view/src/canvas/Flow.tsx、drop.ts |
| 对象内容、细节和媒体绘制 | frontend/view/src/canvas/ObjectBlock.tsx、Media.tsx、TrackMedia.tsx；Waveform.tsx 共享波形算法并保留独立组件 |
| 镜头与换档时机 | frontend/view/src/camera.ts |
| 普通模式与截图等待 | frontend/view/src/capture.ts |

从仓库根执行不启动浏览器的量具回归：

~~~powershell
.venv/Scripts/python.exe -X utf8 -B -m unittest discover -s tests -p test_view_bench.py -v
~~~

其中 Node 可用时会实际执行初始化与命中脚本，检查监听器和窄对象的命中行为；不仅检查 JavaScript 语法。

前端修改后，在 frontend/view 执行 npm run build，包含类型检查、前端测试和网页/内置插件构建。然后回到仓库根，先跑较小的浏览器验收：

~~~powershell
.venv/Scripts/python.exe -X utf8 -B -m unittest discover -s tests -p test_view.py -k test_bench_measures_in_a_browser -v
~~~

再按本页运行性能对照和项目要求的完整回归。不要并行运行多个浏览器性能任务；profiler、trace、截图采集也应与正式计时轮分开，避免测量开销互相干扰。

渲染改动须保持点击、标题、标记、关系线和插件语义；分批细节处理须保留已有内容并取消过期任务；共享画布须控制分块和临时位图内存。性能达标与行为正确是两项独立验收，最终手感还需要用户在正常浏览器确认。
